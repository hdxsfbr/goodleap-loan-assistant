## How to read this document

Each finding carries the lens tags of every reviewer who raised it (first tag is the reviewer whose framing was adopted), the risk as the reviewers described it, and the requirement they demanded of the concept brief, the design document or the prototype. Where reviewers disagreed, the disagreement is stated inside the finding and summarised in the section "Where the reviewers disagree". Every finding also says what to build tonight and what to describe only, because every reviewer weighed its demands against the deadline and the 2 to 3 page limit.

A recurring theme: almost every design-document requirement below costs one sentence or one table row, not a paragraph. The reviewers converged on two cheap carriers for most of them: a single six-row "change surface / owner / what a change touches / where it is versioned" table in the Architecture section, and a single `src/versions.ts` file in the prototype.

## Blockers

### B1. The "feature 2 adds roughly 60%" claim is unbacked; the build-versus-describe split must be decided before any code is written

* **Lens:** `egm-zoom-out`, `egm-design`; dissent from `egm-implementation-readiness` and `egm-structural`, whose findings assume both features are built with concrete defaults
* **Risk:** Component by component the shared pieces are the small ones (LLM client, audit wrapper, web shell, README). The feature-2-only list is PDF ingest, pdf.js positioned text, an OCR path, a quote matcher, a box overlay with coordinate transforms, three extraction schemas, three synthetic PDFs (one image), review-queue and document-management mocks, a reviewer UI, a discrepancy comparator with a tolerance rule and two routes, derived-value formulas and an extraction eval spec. That list is longer than feature 1's unique list and has a far fatter risk tail (coordinate bugs and OCR noise at 2 AM). Feature 2 is at least 100% of feature 1, not 60%. The scarcest resource before tomorrow morning is hours. Separately, the design document has six mandated sections in 2 to 3 pages; two features means two data flows, two failure-mode sets and two eval approaches in every section, halving depth per feature in the primary deliverable. The rubric names "highest-leverage problem, not boil the ocean", and the take-home prefers a focused 1 to 2 hour submission over a sprawling one. The brief's Alternatives table rejects "hybrid" as two shallow halves but never weighs "one deep path built, the other designed".
* **Requirement:** Decide tonight and record the decision in the brief's Analysis section. Two positions were argued:
  * (a) `egm-zoom-out`: build the copilot deep path only. Put extraction in the design document as Phase 2 of the rollout with one paragraph each in Architecture (S3 upload event to SQS to an ECS extraction worker; Textract for geometry; Claude for schema extraction with citations; review task created in JSM via REST; nothing enters the record unconfirmed) and in AI design decisions (the model never returns coordinates; positioned text plus quote matching; failure mode "source not located"). Roughly 200 words, and it earns the technical-depth and ecosystem credit the provenance idea deserves. If the copilot path, guardrail, evals and README are done with time left, add a thin slice: one text-PDF pay stub, Anthropic document citations, value plus quoted text plus page, confirm/flag buttons, no boxes, no OCR, no rendered document.
  * (b) `egm-design` and `egm-implementation-readiness`: build feature 2 at reduced depth: one extraction call per document, positioned text precomputed and committed for all three samples, the reviewer view with boxes, one deliberate "source not located" value, one templated needs-clarification transition; no runtime OCR; evals beyond about ten cases described only.
  * Either way: the design document must state plainly which items are described-only; the README reads as staging, not as a shallow half; and evals are not the thing cut to pay for OCR (see M13). Cutting feature 2 from the prototype also removes the riskiest implied-decision surface in the concept (extracted income shown beside the requested amount), which the brief itself notes when rejecting "extraction only".

### B2. Runtime OCR is out; the precomputed OCR fixture and the three sample documents are the first build task

* **Lens:** `egm-implementation-readiness`, `egm-design`, `egm-comprehension`, `egm-zoom-out`, `egm-structural`

It threatens the under-5-minute local run and makes the demo non-deterministic. Nothing in extraction can be tested until the sample files and the positioned-text source exist, so this is on the critical path of any feature-2 build.
* **Requirement:** Resolve open item 2 as "precomputed". Produce the pay stub once as an image (an HTML page screenshotted, or any editor exported to PNG), embed it in a PDF with `pdf-lib`, run tesseract.js once locally and commit `samples/paystub.ocr.json` (words with bbox and confidence in page pixel coordinates, plus page width and height). Generate the estimate and scope letter as text PDFs with `pdf-lib` from `samples/ground_truth.json`, which doubles as the extraction golden file. Fixed fake names, employer and address; no SSN. The fixture is an adapter in the same `PositionedText` shape as the pdf.js output (M9), so the seam is visible to the grader and rule 7 (both location paths shown) still holds. Keep an optional `npm run ocr` that regenerates with tesseract.js if time remains. Design: Textract in production, consuming the same JSON shape. README states which step was done by hand. If position (a) in B1 is chosen, this finding collapses to "one text-PDF pay stub generated with pdf-lib".

### B3. The audit log is specified as "an entry per model call", but the compliance question is about a homeowner card, which is not a model call

* **Lens:** `egm-codebase-details`, `egm-structural`, `egm-comprehension`, `egm-implementation-readiness`, `egm-design`
* **Risk:** A card is composed from a calculator result, a catalog lookup, a model-written explanation, two guardrail verdicts and a code template. With per-model-call entries and no identifiers named anywhere in the brief, nobody can join those pieces back together; "every borrower-facing message is logged with its inputs" is a promise without a key. The brief says "one audit log", "per model call" and "per turn", which are three different granularities. Re-rendering a card from inputs after a template, catalog or calculator change gives today's card, not that day's. If the entry shape is whatever the code happened to log, the first field rename breaks the Snowflake pipeline and the evals; lending records carry multi-year retention, so entries need a schema version.
* **Requirement:** Define the audit log as an append-only event stream with one root correlation key and a fixed, versioned set of event types. Minimum identifiers on every event: `application_id` (root), `session_id`, `turn_id`, `event_id`, `parent_event_id`, `seq`, `ts` (UTC ISO 8601), `actor {type: contractor | reviewer | system | model, id}`, `schema_version`. Minimum event types: `model.call` (inputs defined as the exact context window the model saw: message ids plus system prompt version and hash; raw output; input, output and cache-read token counts; latency), `tool.call` (calculator, catalog, contractor_profile, documents; `credit_engine` present in the enum and showing zero calls), `guardrail.verdict` (one per layer), `field.proposed` / `field.edited` / `field.confirmed`, `card.rendered` (the complete rendered artifact: explanation, disclosure block, every option's numbers, a content hash, the calculator inputs and outputs, pointers to the `model.call` and verdict events), `document.uploaded`, `extraction.completed`, `review.decision`, `discrepancy.raised` / `discrepancy.resolved`, `application.state_changed`, `context.compacted` (what was dropped from the context window). Large artifacts referenced by key, never inlined; each field carries a PII classification (M7). The compliance query path is stated in the design: filter by `application_id`, `card.rendered` and a date range, then follow `parent_event_id` back to prompt version, context window, tool results and verdicts. Tonight: `src/server/audit-log.ts` exposing only `append` and `list`, a TypeScript event union type that is the schema, an in-memory array plus JSONL append, every service call routed through it, and a half-page `docs/audit-schema.md`. About an hour; most other findings depend on it.

### B4. "Nothing enters the application record unconfirmed" is a UI convention unless the write path enforces it

* **Lens:** `egm-structural`, `egm-implementation-readiness`, `egm-design`, `egm-comprehension`
* **Risk:** If the contractor, reviewer and audit views share one in-memory store and mutate it directly, the concept's central compliance claim is enforced by discipline, and a grader reading the prototype will see the gap. In production the natural implementation (per-field `*_proposed` / `*_source` columns or a JSONB `ai_meta` column on the applications table) alters a table read by the decision engine, the portal screens, Zapier rules and the Snowflake ETL, and puts unconfirmed AI output into the application row, contradicting rule 1. Two writers (the contractor typing, the copilot proposing) target the same fields with no precedence: the copilot re-proposes an already-confirmed field; the contractor corrects themselves ("actually $28K") while the earlier proposal still points at the older message; a manual edit and a proposal land in the same second. The brief does not say what "points at the message" looks like on a touch screen, whether submit is allowed with proposals pending, or how five fields proposed from one sentence avoid five taps in a kitchen.
* **Requirement:** Design: proposals are rows in a sidecar table `ai_field_proposals` (`application_id`, `field_key`, `proposed_value`, `source {kind: message | box | formula, ref}`, `state: proposed | confirmed | edited | rejected | superseded`, `prompt_version`, `audit_event_id`, `confirmed_by`, `confirmed_at`). One `ProposedValue` envelope is shared by both features, whether the source is a chat message or a bounding box. Invariants: at most one live proposal per field per source; the application record holds only confirmed values; a contractor-typed value is never overwritten by a proposal, and a conflicting later statement becomes a proposed change shown as old to new, never a silent replace. Confirmed values reach the application only through the existing write path (the form submit for the copilot; the manual-review confirmation path for extraction), so the application schema and all its consumers are untouched, Snowflake picks up one new table, and rollback is "stop writing proposals". The only write path is a small set of named backend commands (`proposeFieldValue`, `confirmValue`, `editValue`, `rejectValue`, `raiseDiscrepancy`, `resolveDiscrepancy`, `submitApplication`) that enforce state and emit audit events; views are read-only clients of an API. Tonight: `src/server/commands.ts`; the three views as three routes fetching `/api` (the LLM key has to live server-side anyway); the React form holds `{value, state, sourceRef}` per field and renders proposed fields with a distinct badge that is a tap target scrolling to and highlighting the source message; "Confirm all" with per-field dismiss; submit disabled while proposals are pending, with a count ("3 proposed values need confirmation"), which is where the rule becomes visible. Two tests: `confirmValue` on a value with no proposal throws; `submitApplication` with any unconfirmed value throws. Describe only: the old-to-new diff on conflicting statements.

### B5. The discrepancy state machine is undefined, Rule 3's income routing is circular, and the tolerance rule is still open

* **Lens:** `egm-structural`, `egm-comprehension`, `egm-design`, `egm-implementation-readiness`, `egm-codebase-details`; simplification dissent from `egm-zoom-out`
* **Risk:** The demo uploads three documents, so two discrepancies can be open at once (pay stub income versus stated income; estimate total versus requested amount). If "needs clarification" is a stored application-level state, the second discrepancy has no transition to enter and resolving either has no safe transition to leave; this is visible in the demo itself. As a new value of the applications `status` enum it breaks portal screens, the decision-engine trigger, Zapier rules keyed on status and the Snowflake funnel stages. Rule 3 says income discrepancies "go to the document reviewer", but the reviewer is the one who found the discrepancy, so a fresh reader cannot say who receives the question. With no tolerance, every pay stub disagrees with stated income ($84,760 annualized versus $85,000 stated), every application enters "needs clarification", the queue floods, and feature 2 becomes slower than today. If the clarification question is model-written it is the easiest implied-decision leak in the concept ("the income shown appears insufficient for this amount"), and that text reaches the contractor and, via them, the homeowner. The JSM task has its own status; two years in, staff close tickets directly and applications stay stuck. If extraction compares against a stated value that is still an unconfirmed copilot proposal, the comparison is against a value that may be rejected a minute later. To a contractor, an undefined "needs clarification" label reads as a soft rejection.
* **Requirement:** Resolve in the brief before the design draft:
  * Discrepancies are per-value records (field, stated value with source pointer, extracted value with source pointer, rule id and tolerance version, difference absolute and percent, routing target, status `open | resolved | waiting_on_stated_value`, resolver, resolution note, `review_task_id`). The application's "needs clarification" is derived (any open discrepancy), never stored as a transition; the application stays in the existing "documents under review" status, which already blocks the decision engine; the portal shows a banner driven by the sidecar. A first-class status is a phase-3 change with a consumer audit.
  * Routing target and tolerance are properties of the field in the document schema, not a switch on document type. Name the recipient per discrepancy type in one sentence each. Suggested: income goes to the contractor with a templated question to relay to the homeowner (the contractor is the only party the portal reaches); estimate and scope discrepancies go to the contractor directly.
  * Comparisons run when the reviewer confirms the extracted value, against the confirmed stated value; if the stated value is unconfirmed, the discrepancy waits. Review tasks are per application (the check needs all three documents plus the stated values), not per document.
  * Reason codes are a fixed enum; the clarification question is a code template per reason code, never model text; the reviewer edits it before sending and never sees a verdict word in the UI. `application.state_changed` and `discrepancy.raised` events carry the two compared values with their source pointers, the rule id and tolerance version, the routing target, and the question text with its origin (template id).
  * Tolerance defaults in `tolerances.json`, marked Compliance and Credit Ops owned, versioned (M6): annualized income outside plus or minus 10% or $5,000, whichever is larger; requested loan amount greater than the estimate total by more than 5% (less is fine, it is a down payment); name and employer normalized token overlap below 0.6; pay period end date older than 60 days; annualize by extracted pay frequency (weekly 52, biweekly 26, semimonthly 24, monthly 12), and if frequency is not located do not annualize, raise "pay frequency not located". Inside tolerance: no routing, difference shown in the reviewer view. `egm-zoom-out` dissent: for the prototype, one percent band for income and exact match for amounts is enough, and per-field rules are two sentences of v2 in the design; `egm-comprehension` agrees. Both are compatible: ship one table with two rows tonight and describe the rest.
  * Define the state wherever it appears: "Needs clarification: a reviewer found a difference between a document and the application and has sent a question. No decision has been made." Show the question and recipient on the contractor's application status.
  * JSM is a projection: the task id is stored on the discrepancy, resolution flows backend to JSM, and the JSM webhook path is idempotent and advisory (describe only).
  * Tonight: `src/domain/discrepancy.ts` with the record type and `deriveApplicationStatus(app)`; `route` and `tolerance` on schema fields; one templated question; the discrepancy panel shows document value and application value side by side, the difference, and the rule as text ("differs by more than 10%"); one test: two open discrepancies, resolve one, status still "needs clarification". The demo shows one transition with its templated question.

### B6. The stack and the implementation defaults must be adopted tonight, not chosen

* **Lens:** `egm-implementation-readiness`
* **Risk:** The brief fixes TypeScript, Node and React and nothing else. Every hour spent choosing tonight is lost, and a native-module install failure on the grader's machine breaks the 5-minute rule. Persistence beyond the session is a non-goal, but a `tsx watch` restart mid-walkthrough would wipe the queue and the audit log.
* **Requirement (default to adopt as-is):** One repository, one `package.json`, two directories: `web/` (Vite + React + TypeScript) and `server/` (Express + TypeScript run with `tsx`); `npm run dev` runs both via `concurrently`; Vite proxies `/api` to port 3001; setup is `npm install && cp .env.example .env && npm run dev`; pinned Node version in `engines` or `.nvmrc`. Anthropic SDK with tool use for the copilot (tools: `get_products`, `calculate_payment`, `propose_field_fill`, `build_homeowner_card`) and one JSON-schema-constrained extraction call per document, validated with Zod after parse; on validation failure retry once, then mark the task `extraction_failed`. One dated Sonnet-class snapshot for copilot and extraction, a Haiku-class snapshot for the judge, with latency and cost reasoning in the design. PDF viewer: `react-pdf` (pdf.js) with boxes as absolutely positioned divs scaled by the rendered viewport. Positioned words for text PDFs: `pdfjs-dist` `getTextContent()` server-side; items are runs, not words, so split each run into words proportionally by character count and note the approximation. Tests: vitest. No database, no Docker, no Next.js (SSR and pdf.js do not mix under time pressure), no native modules (`canvas`, `sharp`, native tesseract bindings). In-memory state seeded from `samples/seed.json`; every mutation appends to `data/audit.jsonl` and rewrites `data/state.json`; `POST /api/reset` restores the seed; the README's run command does not use watch mode. Serve the API and the static frontend from one process.

## Major

### M1. The 30-second payment promise has no latency budget, and the pipeline as designed cannot meet it

* **Lens:** `egm-design`, `egm-comprehension`, `egm-codebase-details`
* **Risk:** The payment-answer path is three sequential model calls (tool-use call, explanation call, judge call) plus 15 to 20 seconds of tablet typing, plus possibly a clarifying turn when amount or term is missing. Nothing can stream, because the judge runs on finished text. Estimate 8 to 12 seconds typical and about 20 seconds p95 for a Sonnet-class model on uncached 10K-token prompts, before typing; a guardrail retry doubles it. No latency budget exists, so the promise is unverifiable, and the rubric grades latency by name.
* **Requirement:** The design states a budget: calculator and catalog under 100 ms; numbers and the disclosure block on screen within about 3 seconds of the question being understood; model explanation plus judge under about 10 seconds p95; 30 seconds end to end including typing. Render in stages: the calculator result and the code-templated disclosures depend on no model text and need no judge, so they render the moment the tool call returns; only the model's prose waits behind the judge. This is also the strongest available demonstration of "disclosures woven in". Judge on the small model with a classification-only prompt (about 1K in, 50 out). Prompt caching on the fixed prefix (rules, catalog, tool schemas). Prototype: a "Show payment options" button that calls the calculator directly once amount and project type are on the form, with no model in the loop, so the promise holds during an API outage; three or four one-tap suggested prompts seeding the panel ("Payment options for this project", "Explain deferred interest", "What documents are needed"); a stepwise status line that mirrors the real pipeline ("Finding matching products... Calculating payments... Checking wording...") so a wait reads as work; p95 per step and tokens per turn logged on `model.call`. Describe only: docking the copilot at the product-selection step with the comparison precomputed from the form; tablet-portrait drawer; streaming with the deny-list applied token by token and the judge on the final text, and which mode ships and why.

### M2. The deny-list as specified will block correct answers and its own disclosure template

* **Lens:** `egm-design`, `egm-zoom-out`, `egm-structural`
* **Risk:** "approved" matches "subject to credit approval" in the brief's own template; "free" matches "feel free to ask"; "no interest" and "interest" appear in every honest promo explanation ("no interest accrues during the promotional period if the balance is paid in full"), and a regex cannot see "without the promo caveat", so that case silently shifts to the judge. The copilot will refuse to explain the product the feature exists to explain. Each false positive costs a retry (5 to 10 seconds, more tokens); at a 10% rate it breaks the 30-second promise for one homeowner in ten. A false negative is a borrower reading "you'll be approved" on a card, with unbounded cost. "A handful of adversarial prompts" cannot support any claim about either rate. Within a year a deny-list embedded in the guardrail module is a list of regexes with exceptions, a mini-DSL with no owner and no regression set.
* **Requirement:** Deny-list only unambiguous verdict and approval terms (approved, pre-approved, guaranteed, qualify, you're eligible), as word-boundary regexes with an explicit allow-list of phrases; applied to model-written spans only, never to template text or catalog product descriptions; the judge handles marketing nuance and promo caveats on prose outputs only (the guardrail has no meaning for structured extraction output, and the brief's "every model-written text" should say so). The deny-list is data, not code: a versioned JSON file with entries (pattern, reason, added by, date, allowed contexts), owned by Compliance. The deny-list and the judge are two implementations of one `GuardrailCheck` contract (`check(text, surface) -> Verdict`) with explicit precedence: either block is final; a disagreement is logged as a tuning signal. Make the asymmetry explicit in the design: a cheap bounded false positive (retry once, then template fallback) versus an unbounded false negative (the deny-list is the floor the judge cannot lower). Tonight: `src/guardrail/denylist.json`, `src/guardrail/index.ts` with the interface and two implementations, `tests/guardrail.test.ts` with about ten must-block cases and about five must-pass cases that include the rendered disclosure block and a 0% promo explanation; the must-pass half is the piece most likely to be missing and the one that makes the list maintainable. Design: a pre-launch eval specification of at least 100 labeled outputs, half non-compliant across implied approval, pressure language and uncaveated promo claims, with judge recall at least 0.95 and false-positive rate at most 5% as launch gates, and shadow-mode logging of both verdicts in production.

### M3. Guardrail trip behaviour and the out-of-scope refusal are unspecified, so the guardrail is invisible and the contractor is left with nothing to say

* **Lens:** `egm-zoom-out`, `egm-codebase-details`, `egm-comprehension`, `egm-design`
* **Risk:** The brief says both verdicts are logged and never says what happens next or what the contractor sees. Two situations are conflated: (a) the model's output tripped the list or the judge, where the contractor did nothing wrong and "guardrail violation" with the homeowner watching is embarrassing; and (b) the contractor's input is out of scope ("will they be approved?"), where a flat refusal leaves them with nothing to say in the kitchen. If the judge (a second Anthropic call per turn) times out, fail-open silently ships unguarded text to a kitchen; fail-closed with no log looks like a dead copilot. Silent blocking makes the required guardrail invisible in the demo. The rubric explicitly grades "how you handle the messy realities of LLM output in a regulated context".
* **Requirement:** On a trip: regenerate once with the verdict's reason fed back to the model; if it fails again, show a fixed, Compliance-owned fallback that still answers what can be answered (the options table renders regardless), plus a quiet marker under the reply ("Wording adjusted to comply with lending rules. View in audit") linking to the entry that shows draft, verdict and final. Both attempts and the blocked raw text are retained; the blocked text is the eval dataset. Judge unavailable is fail-closed with its own outcome code so it is distinguishable from a block. Out-of-scope: a fixed reply shape enforced by the prompt and checked by a test: one sentence that approval decisions are made by GoodLeap's credit team after submission, then two concrete things the copilot can do now (show payment options; list what the application needs); no reasoning about likelihood, no "should be fine", no restating income. Print the exact fallback and refusal text in the design document; it is the most-graded sentence in the system. Each `guardrail.verdict` event carries layer (`denylist | judge`), verdict, matched terms or judge rationale, `denylist_version`, `judge_prompt_version`, judge model id, latency and outcome (`pass | blocked | judge_unavailable`). Metrics per prompt and deny-list version: deny-list hit rate, judge block rate, disagreement rate in both directions (judge blocks what the list passed means add terms; list blocks what the judge passed means false-positive review), `judge_unavailable` rate, regenerate-then-fallback rate, shown as counts in the audit view. The README demo script includes one message for each case. About an hour.

### M4. One provider, a judge on every turn, and no degradation policy: an Anthropic outage takes down the copilot, extraction and the judge at once

* **Lens:** `egm-design`, `egm-codebase-details`, `egm-structural`
* **Risk:** Because the judge is also down, the brief's own rule that every model-written text passes the guardrail means the whole copilot goes dark rather than degrading. The judge shares a model family with the generator, so blind spots are correlated. Model ids are deprecated on roughly yearly cycles, and the two behaviours the design depends on most, exact-quote fidelity in extraction and tool-call formatting, are the ones that move between versions. If prompts, model ids, temperature and SDK calls are scattered across copilot, extraction and judge, a version bump is a cross-cutting change with no way to see what regressed. The binding Anthropic quota at peak is input tokens per minute, not requests; the brief says nothing about rate limits or caching.

### M9. Quote matching has four unnamed failure modes and no algorithm, and the two location paths put boxes in different coordinate systems

* **Lens:** `egm-design`, `egm-implementation-readiness`, `egm-structural`, `egm-comprehension`; alternative from `egm-zoom-out`
* **Risk:** (a) OCR noise: the model reads "$4,250.00" correctly from the image while the OCR text says "$4,25O.OO" or splits the token, so the exact-quote match fails on precisely the values that matter; or, if the model sees only OCR text, it quotes the noise verbatim, the box draws, and the value is wrong. (b) Repeated values: pay stubs repeat the same number in Current and YTD columns and estimates repeat line amounts in subtotals, so the first match draws the wrong box with full confidence. (c) pdf.js returns text items in content-stream order, so table cells and multi-column layouts break a line-level quote. (d) A quote without a page index is ambiguous on multi-page documents. The text-PDF path yields PDF points with a bottom-left origin at page scale; the OCR path yields image pixels with a top-left origin; the brief promises to show both, so without normalization one of the two sample documents will have boxes drawn in the wrong place, which misleads the reviewer more than no boxes. Textract in production returns a third shape (WORD and LINE blocks); an ad hoc matcher written against tonight's two sources drops its match rate on the swap with no alarm. A fuzzy threshold not logged on the value means the box cannot be trusted later.
* **Requirement:** One `PositionedText` intermediate representation (page, words in reading order, each with text, bbox stored as page-relative fractions 0 to 1 with top-left origin regardless of source, confidence); every source (pdf.js, the OCR fixture, future tesseract or Textract) is an adapter producing it, and the matcher sees only the IR. Make the model select, not generate: feed positioned text as indexed lines grouped by y-coordinate (for example "p1 L07: Gross Pay | 4,250.00 | 51,000.00") and have the structured output return `{page, line, token span, quoted_text}`; the backend verifies the quote against the referenced span, which keeps rule 5 intact and makes matching deterministic and unambiguous. Normalization is a named pure function with tests: lowercase, drop `$` and `,`, strip punctuation except `.` `/` `-` inside numbers and dates, collapse whitespace, fold O/0 and l/1, join hyphenated line breaks. Fallback window match when the span is absent: order words by line (y within half a word height) then x; slide a window of the quote's token count plus or minus one; token score 1 for exact else Levenshtein ratio, a token matches at 0.8 or above; numeric tokens must match exactly after normalization; accept the best window with mean score 0.85 or above spanning at most two lines. Reject the quote if the normalized value is not contained in the normalized quote (a hallucinated pointer). Require a disambiguating anchor (row label or column header) for monetary fields. The match result carries method (`exact | normalized | fuzzy`) and score and is stored on the proposed value; a visible "approximate location" box style sits between "located" and "source not located". Box = union of matched word boxes, drawn on the same canvas pdf.js renders. Derived values (annualized income) show a formula string plus the input proposal ids. "Source not located" rate per document type and per adapter is a monitored metric in the monitoring section. Document the known gap: an OCR error inside the value yields a wrong but located value, which is what the reviewer is for. `egm-zoom-out` alternative if boxes are cut: send the PDF to the Messages API as a document content block with citations enabled and a tool schema for the fields; the API returns `page_location` citations (`cited_text`, page range) the system verifies with a plain string match; the reviewer sees value, quoted text and page; describe Textract geometry matched against cited text as the production method for scanned documents. Tonight (if boxes are built): `src/extraction/positioned-text.ts`, `adapters/pdfjs.ts`, `adapters/ocr-fixture.ts`, `match.ts` with four normalization tests (whitespace, currency, hyphenated line break, case); fraction-normalized coordinates are ten lines and prevent the demo's most visible failure.

### M18. Six mocks, two or three with no caller, no seam, and a decision-engine mock one refactor away from being rendered

* **Lens:** `egm-structural`, `egm-zoom-out`, `egm-codebase-details`
* **Risk:** The demo ends at "submitted", so the credit decision engine mock is never called; income verification is via documents, so the Plaid mock is never called. Building request/response shapes nobody consumes is cost with zero rubric credit, and "mocked services" risks becoming separate mock HTTP servers. If the copilot imports `products` from a mock file directly, the swap to the real catalog ripples through every caller and "integrates conceptually with existing APIs" is invisible in the code. A decision-engine mock that returns "approved" is one refactor away from being rendered. If the audit view shows a catalog lookup and an LLM call identically, a grader cannot tell mock from real, and "the model never computes a number" is unverifiable from the screen.
* **Requirement:** One in-process module with an in-memory store; no mock HTTP servers. Each external system is a TypeScript interface (`src/services/<name>/types.ts`) with one mock implementation (`mock.ts`) and a comment naming the real endpoint and auth; callers depend only on the interface; one composition root (`src/services/index.ts`) selects implementations from `MOCKS=true` in `.env.example`. For the uncalled APIs (credit engine, Plaid) a typed interface stub with a one-line comment naming where it would be called; this reconciles the `egm-zoom-out` "do not build uncalled mocks" position with the `egm-structural` "six interfaces are cheap and are the most direct evidence for build-versus-mock judgment" position. The decision engine interface has no method any UI code calls; its only consumer is `submitApplication`, which records "submitted" and nothing else. Every mock response carries a `_mock` envelope `{service, fixture_id, mock_version, simulated_latency_ms}`; every `tool.call` event records it; the audit view renders a MOCK badge on those rows and a LIVE badge with the Anthropic request id, model id, tokens and latency on `model.call` rows; the audit view shows a `credit_engine` call count that reads zero. Design: a short table mapping each existing API to its call site and whether the prototype calls it, stubs it or stops before it. If time: an env toggle (`MOCK_FAIL=catalog`) that makes one mock fail so the graceful-degradation path can be shown live; otherwise describe it.

### M19. Per-document-type schemas: three hand-written pipelines today, a five-file change for the fourth type, and no slot-mismatch check

* **Lens:** `egm-structural`; simplification dissent from `egm-zoom-out`
* **Risk:** The fourth document type (bank statement, W-2, 1099, proof of homeownership) will arrive within months. If each type is a separate prompt, a separate TypeScript type, a separate reviewer panel, a separate discrepancy rule and a separate routing branch, adding one is a five-file change across four owners, and changing a field on an existing type requires re-reviewing all five. If classification is by upload slot (the contractor picked "pay stub"), a mislabeled upload produces confident proposals with boxes drawn on the wrong kind of document.
* **Requirement:** Each document type is one declarative schema (fields with id, label, type, description for the model, `compareTo` stated field, tolerance, route, derived fields with formula and inputs); the extraction prompt, output validation, reviewer panel and discrepancy rules are all derived from the schema; a fourth type is a schema file, a sample document and an eval set, with no new UI code. The extraction prompt first confirms the document matches its slot and returns "document type mismatch" rather than values when it does not; describe this, build it only if trivial. Tonight: `src/extraction/schemas/{pay_stub,estimate,scope_letter}.ts`, one `buildExtractionPrompt(schema)`, one generic reviewer panel iterating `schema.fields`; this is justified by simplicity rather than speculation, since one generic panel is less work tonight than three hand-written ones. If the reviewer view is already half-built by hand, keep it and state the schema-driven version as the design. `egm-zoom-out`: if the thin slice in B1(a) is chosen, one document type (pay stub) is enough and the schema-driven design is described, not built.

### M20. The reviewer's confirm / correct / flag loop is undefined and its decisions are not captured as data

* **Lens:** `egm-comprehension`, `egm-codebase-details`
* **Risk:** "Opens the document with the boxes drawn on it and confirms, corrects or flags each value" leaves the loop undefined: is the value list beside the page, and does selecting one jump to its box? Does "correct" mean typing over the value, and what happens to the box? Does "flag" need a reason? One task per document or per application? Is there a confirm-all (the contractor side has one; a fresh reader assumes symmetry, and here it would defeat the purpose)? When is the review done? "Flag" with free text is not a metric. Review is the only place the system gets ground truth for free, and without per-field rates the team cannot tell whether a bad week is the OCR path, the matcher, the prompt or the sample documents.
* **Requirement:** Layout: one task per application with a tab per document; values on the left grouped by schema field, page on the right; selecting a value scrolls to and highlights its box, clicking a box selects its value. Semantics: Confirm = value as extracted. Correct = inline edit; the box stays as "read from here"; state becomes corrected-by-reviewer. Flag = reason from a fixed enum rendered as a select, not a text box (`illegible`, `source_not_located`, `mismatch_with_stated`, `wrong_document_type`, `missing`, `other`) plus optional note. No confirm-all; say in the design why the reviewer side has none while the contractor side does. Completion: "Complete review" enabled only when every value has a state; the outcome is "documents reviewed" or "needs clarification" (B5), shown as the application status in the contractor view. `review.decision` carries `field_id`, `document_type`, `proposed_value`, `final_value`, action, reviewer id, time since task creation, reason code; `extraction.completed` carries, per field, the location path (`pdfjs | ocr`), match status and OCR engine version. Metrics per document type and field: confirm/correct/flag rate, numeric correction magnitude, source-not-located rate split by location path, queue time (created, first open, decision), needs-clarification rate and time to resolve. Describe only: keyboard shortcuts, zoom, multi-page documents beyond the single-page samples.

### M21. The audit view is a record, not a view; "per turn" misses extraction and cannot show a screen

* **Lens:** `egm-comprehension`, `egm-codebase-details`; dissent from `egm-zoom-out` (a collapsible-JSON page suffices; spend the polish on the contractor view and the homeowner view, where Design Taste is graded)
* **Risk:** The audit entry as listed is a record, not a view. "What the system said and why, per turn" as JSON does not let a compliance officer reconstruct an interaction; "per turn" implies chat only, while the extraction path also writes AI-produced values and must appear. For the homeowner card, "exactly what the system said" is a screen, not a string; a log line cannot show it.
* **Requirement:** Organise the view application, then cards, then provenance chain, with the turn list secondary (the compliance question is card-first; the per-turn list is the engineer's view). Timeline per application: per chat turn, what the contractor asked, which tools ran with what inputs (one line), the model's draft, each guardrail verdict with its reason, what the contractor saw, what the homeowner saw if a card was shown; per document, each value, its box or not-located, the reviewer action, who and when. Raw JSON behind an expander per entry. A "Borrower-facing only" filter. Re-render the homeowner card from its stored inputs (calculator output, explanation text, template version) exactly as shown: free if the card is a pure component of its props, so decide that now, before writing the card. "Prompt version" is a visible, real identifier. About an hour if the log is structured from the start (B3); if it is not, take the `egm-zoom-out` position and ship the collapsible-JSON page linked from the contractor view.

### M22. Terms a fresh reader will not understand, and three names for one person

* **Lens:** `egm-comprehension`
* **Risk:** The brief defines most terms by example or a single clause, which works for the author but not for a grader reading a 2 to 3 page design document cold or a reviewer meeting a state label. At risk: "proposed" (a state with an undefined lifecycle), "needs clarification", "source not located", "homeowner card", "verdict word" (defined only by example), "application record" (the form, or a backend object?), "review task", "model judge", "deep path", and three names for one person ("homeowner", "applicant", "borrower"). "Deferred interest" and "promo end date" are undefined for the homeowner, who is the one who needs them. The page budget does not allow a glossary section.
* **Requirement:** Design document: define on first use in one clause each; no glossary section. One name for the person: "homeowner" everywhere, "borrower" only when quoting the regulation. Define "verdict word": any word that states or implies whether the applicant will be approved, with the list the deny-list enforces. Put the full state vocabulary (field states, review states, application states) in a supporting `docs/` file and link it from the design document. UI: every state label carries a one-line caption, inline or on tap (proposed, confirmed, corrected, flagged, source not located, needs clarification, documents under review); the homeowner view explains each promo mechanic in one sentence beside the option that uses it. README: call the scenario a "demo walkthrough", not a "deep path".

## Nit

### N1. The justification "vision models return text, not coordinates" is stale and will cost ecosystem-fluency credibility

* **Lens:** `egm-design`
* **Risk:** Several current models return bounding boxes with uneven reliability, and a fluent reviewer will notice. The decision itself is right.
* **Requirement:** Reword to "model-returned coordinates are unverifiable and carry no provenance; positioned text from the document plus quote verification gives exact boxes and a testable failure mode." State why Textract over a vision model for production geometry: already on AWS, returns word geometry for PDFs and images, and its output is a data artifact rather than a model claim.

### N2. Document sprawl around a 2 to 3 page primary deliverable

* **Lens:** `egm-zoom-out`
* **Risk:** The brief commits to supporting documents for field schemas, the eval spec, disclosure templates and the provenance method, plus a separate deployment section and an AI usage document. None of these are graded on their own; all consume the night.
* **Requirement:** README (required), design document (required), one short AI-usage note (required by the portal). Schemas live in code as zod types, the disclosure template lives in code, eval cases live in the JSON fixture; the code is the documentation. The only supporting files the other lenses asked for are a half-page `docs/audit-schema.md` (B3), `docs/evals.md` (M13) and the state vocabulary (M22); each is a short index pointing at a type file. Fold deployment on ECS/RDS/S3/SQS into the architecture section, which already asks how the design fits the existing stack.

### N3. Copilot field proposals record the confirmation but not the edit

* **Lens:** `egm-codebase-details`
* **Risk:** A contractor who changes every proposed value is the early signal that the extraction-from-conversation prompt is wrong, and it is invisible if only the final confirmed value is kept.
* **Requirement:** `field.proposed` stores the proposed value and the message id; `field.edited` stores before and after; `field.confirmed` stores the final value and actor. Metrics: proposal acceptance rate and edit rate per form field per prompt version. Three events instead of one, trivial once B3 exists. Describe only: the alert on edit rate.

### N4. Actor identity is absent from the audit log because the prototype has no login

* **Lens:** `egm-codebase-details`
* **Risk:** A compliance reconstruction without "who" is incomplete.
* **Requirement:** The prototype uses a fixed demo contractor id from the mocked contractor profile service and a fixed demo reviewer id, stamped as actor on every event, and the README says so. The design states that production takes both from the portal session and that the homeowner is never identified by the assistant, only by `application_id`. Two constants.
